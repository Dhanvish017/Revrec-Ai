# Synthetic Payment Retry Dataset

`data/payments.csv` is generated by [`scripts/generate_dataset.py`](scripts/generate_dataset.py).
It is **synthetic** (no real customer or transaction data), but the fields are
deliberately wired together with realistic, documented relationships so the
data is usable for training/evaluating a retry-success classifier rather than
being random noise.

Regenerate with:

```
python scripts/generate_dataset.py
```

The generator uses a single seeded `random.Random(42)` instance, so it is
fully reproducible: re-running it produces a byte-identical CSV. Row count is
12,000 (`N_ROWS` in the script), comfortably above the 10,000-row minimum.

## Schema

| column | type | description |
|---|---|---|
| `transaction_id` | string | unique id per failed-payment event (`T0000001`, ...) |
| `customer_id` | string | id of the customer who owns the payment (`C00001`, ...) |
| `customer_segment` | categorical | `new` / `returning` / `loyal`, derived from tenure + prior payment count |
| `account_age_days` | int | customer account age at the time of the event |
| `prior_successful_payments` | int | count of prior successful payments for this customer |
| `payment_method` | categorical | `credit_card`, `debit_card`, `paypal`, `bank_transfer`, `digital_wallet`, `upi` |
| `transaction_amount` | float | log-normal transaction amount (median ≈ $49) |
| `original_failure_at` | ISO timestamp | when the original payment attempt failed |
| `failure_reason` | categorical | why the original attempt failed (see below) |
| `retry_attempt_number` | int (1-3) | which retry attempt this row represents |
| `retry_window_minutes` | int | minutes between original failure and this retry |
| `retry_window_bucket` | categorical | `immediate` (<5m), `short` (5-60m), `medium` (1-24h), `long` (1-7d) |
| `retry_at` | ISO timestamp | `original_failure_at + retry_window_minutes` |
| `hour_of_day` | int (0-23) | hour of `original_failure_at` |
| `time_of_day_bucket` | categorical | `night` (0-5), `morning` (6-11), `afternoon` (12-17), `evening` (18-23) |
| `retry_success` | int (0/1) | **target** — whether the retry succeeded |

## Generation approach

1. A fixed pool of 4,000 synthetic customers is created first, each with a
   stable `customer_segment`, `account_age_days`, `prior_successful_payments`,
   and a preferred `payment_method`. Segments determine the ranges these are
   drawn from (`new`: 0-90 days / 0-2 prior payments, `returning`: 91-720
   days / 3-20 prior, `loyal`: 721-3000 days / 21-200 prior).
2. Each of the 12,000 rows samples a customer from that pool, weighted so
   customers with more prior payments (i.e. more established, `loyal`
   customers) show up more often — mirroring how a real retry log would have
   repeat customers, not a fresh customer per row.
3. `payment_method` is the customer's preferred method 90% of the time, and a
   random other method 10% of the time (occasional card/wallet switching).
4. `failure_reason` is drawn from a categorical distribution whose base
   weights are adjusted (multiplicatively) by `payment_method`,
   `customer_segment`, and `time_of_day_bucket` — see "Encoded relationships"
   below.
5. `retry_window_bucket` (and the concrete `retry_window_minutes` within it)
   is drawn independently of the other fields — bucket choice is generic
   (40% immediate / 30% short / 20% medium / 10% long), and does not itself
   depend on `failure_reason`.
6. `retry_success` is drawn from a logistic model: a base success-log-odds
   per `failure_reason` is adjusted additively (in log-odds space) by
   `payment_method`, `customer_segment`, `time_of_day_bucket`,
   `retry_attempt_number`, and a `failure_reason` × `retry_window_bucket`
   interaction term, plus Gaussian noise (`sigma=0.3`) for unexplained
   variance. The result is passed through a sigmoid and used as a Bernoulli
   success probability.

## Encoded relationships (the "why" behind the numbers)

- **Failure reason is the dominant driver of retry success.** Base success
  probabilities (before any adjustment) range from `fraud_suspected` (4%,
  retrying rarely helps a fraud hold) and `expired_card` (8%, needs an
  out-of-band card update) up to `network_error` (80%, usually transient) and
  `incorrect_cvv` (55%, simple user re-entry error).
- **Retry window matters, but its effect flips sign by failure reason** — a
  short retry window is *not* universally best:
  - `insufficient_funds`, `expired_card`, `card_not_activated` benefit from
    waiting (funds get replenished / cards get updated / activation
    completes over time) → success rises with a longer window.
  - `network_error`, `processing_error`, `incorrect_cvv` are best retried
    quickly, before the transient condition or the customer's attention
    fades → success falls with a longer window.
  - `fraud_suspected` and `bank_decline_generic` are largely insensitive to
    timing since they typically require manual review either way.
- **Payment method shifts both which failures occur and how likely a retry
  is to succeed.** E.g. `bank_transfer` sees more `processing_error` /
  `network_error` and fewer `incorrect_cvv` (no CVV concept), and has a lower
  overall success log-odds (-0.4) than `paypal` (+0.3) or `upi` (+0.35),
  reflecting that card-network retries tend to be smoother than bank-rail
  retries.
- **Customer history matters.** `loyal` customers get a success log-odds
  bonus (+0.4) over `new` customers (-0.5) — established customers tend to
  have valid, current payment details and respond faster to update prompts.
  Segment also shifts failure-reason mix: `new` customers see more
  `incorrect_cvv` / `fraud_suspected` (unfamiliar or freshly-added payment
  methods), `loyal` customers see more `expired_card` / `insufficient_funds`
  (natural card aging / broader spending).
- **Time of day matters.** Overnight (`night`, 0-5h) retries have both a
  different failure mix (more `network_error` / `processing_error`, echoing
  bank batch-processing and maintenance windows) and a lower success log-odds
  (-0.5) than business hours (`afternoon`, reference / 0.0) — support
  channels that can resolve edge cases are largely unavailable overnight.
- **Repeated retries have diminishing returns.** Each additional attempt on
  the same failure applies a success log-odds penalty (-0.3 for attempt 2,
  -0.6 for attempt 3), reflecting that a failure which didn't resolve on the
  first retry is more likely to need out-of-band intervention.
- **Transaction volume is not uniform through the day.** `hour_of_day` is
  sampled from a fixed weight curve that is low overnight and peaks in the
  evening (see `HOUR_WEIGHTS` in the script), rather than being uniform
  across 24 hours.

## Known simplifications / caveats

- All relationships are hand-specified (logistic weights chosen to produce
  plausible, monotonic effects), not fit from real processor data — treat
  absolute probabilities as illustrative, not calibrated to any real
  gateway's true retry-success rates.
- `retry_window_bucket` selection does not depend on `failure_reason` in this
  version (i.e. the data does not assume merchants already retry
  optimally) — this is intentional, so a model trained on this data can
  learn the window/reason interaction rather than have it hidden by
  selection bias.
- Only a single retry event is modeled per row; multi-retry sequences for the
  same original failure are not chained together (each row's
  `retry_attempt_number` is drawn independently, not incremented across
  repeated rows for the same failure).
